# backend — platform API

**Status:** Milestone 2 in progress. Implemented: project scaffold with
health and build-info endpoints (2.1); PostgreSQL with Flyway migrations and
Testcontainers integration tests (2.2); model registry API (2.3); dataset
file storage (2.4, internal: the upload endpoints come with 2.6 and 2.7);
analytics engine client (2.5, internal); reference registration (2.6);
monitoring runs (2.7): asynchronous drift runs with a status API.

Spring Boot application that will expose the public REST API, store models,
datasets, reference profiles and monitoring results in PostgreSQL, and call
the [analytics](../analytics/) engine to do the statistics. It is the only
component that owns persistent state. See
[ARCHITECTURE.md](../ARCHITECTURE.md).

## Local setup

Requires a Java 21 JDK and a running Docker daemon (the tests start
PostgreSQL in a container). Maven itself is fetched by the wrapper.

```bash
cd backend
export JAVA_HOME=$(/usr/libexec/java_home -v 21)   # macOS; any JDK 21 works
./mvnw verify                                       # compile, test, format check
```

## Database

- **Flyway owns the schema** (`src/main/resources/db/migration`).
  `spring.jpa.hibernate.ddl-auto=validate`: Hibernate checks that entities
  match the tables and refuses to start otherwise, but never changes them.
- **Applied migrations are immutable.** `validate-on-migrate` makes startup
  fail if an applied file was edited; change the schema with a new
  `V<n>__description.sql`.
- **Tables appear with the feature that uses them.** V1 creates
  `monitored_model` (2.3), V2 `dataset` (2.4), V3 `reference_profile` (2.6);
  runs get their own migration later.
- IDs are UUIDs generated by the application: not guessable, and known
  before the insert.
- Constraints are enforced in the database too (unique name, non-blank name,
  allowed task types), so invalid rows cannot be written by any code path.
- Maven resolves dependencies from Maven Central only: `flyway-parent`
  declares two private Redgate repositories, which `pom.xml` redeclares as
  disabled.

## Model registry API

| Method | Path | Success | Errors |
|--------|------|---------|--------|
| `POST` | `/api/v1/models` | `201` + `Location` header + model | `400`, `409`, `415` |
| `GET` | `/api/v1/models/{id}` | `200` model | `400` (not a UUID), `404` |
| `GET` | `/api/v1/models?page=0&size=20` | `200` page, sorted by name | `400` (page < 0, size not 1–100) |

```bash
curl -i -H 'Content-Type: application/json' localhost:8080/api/v1/models -d '{
  "name": "credit-risk",
  "taskType": "BINARY_CLASSIFICATION",
  "targetColumn": "defaulted",
  "predictionColumn": "default_probability"
}'
```

```json
{"id": "01a1feec-582f-7126-883a-4d3afc6e888e", "name": "credit-risk",
 "taskType": "BINARY_CLASSIFICATION", "targetColumn": "defaulted",
 "predictionColumn": "default_probability", "createdAt": "2026-11-21T16:24:24.364421Z"}
```

**Request rules** (invalid input is rejected, never silently corrected):

| Field | Rule |
|-------|------|
| `name` | Required. 1–100 lowercase letters, digits or hyphens, starting and ending with a letter or digit (`credit-risk-v2`). Unique. |
| `taskType` | Required. `BINARY_CLASSIFICATION`, `MULTICLASS_CLASSIFICATION` or `REGRESSION`. |
| `targetColumn`, `predictionColumn` | Optional, up to 255 characters. Spaces inside are allowed (`mean radius`); blank values, leading/trailing whitespace and line breaks are not. They must be different columns. |
| other fields | Rejected, so a typo such as `"tasktype"` is an error rather than ignored. |

**Response:** `id` is a time-ordered UUID (version 7). `createdAt` is an
ISO-8601 UTC instant with microsecond precision, the precision PostgreSQL
stores, so `POST` and a later `GET` return identical values. A page is
`{"items": [...], "page", "size", "totalItems", "totalPages"}`.

**Uniqueness under concurrency:** the name is protected by the database's
unique constraint rather than a check-then-insert, so concurrent requests
for the same name create exactly one model; the others get `409` (tested
with 8 parallel requests).

### Errors

All errors are RFC 9457 `application/problem+json`, using the same
`urn:driftwatch:problem:` types scheme as the analytics engine:

| Status | `type` suffix | When | Extra fields |
|--------|---------------|------|--------------|
| 400 | `invalid-request` | Body fails validation | `errors: [{field, message}]`, sorted |
| 400 | `malformed-request-body` | Not JSON, unknown field, or unknown enum value (the detail lists the allowed values) | |
| 400 | `invalid-parameter` | Bad path or query parameter (`'id' must be a UUID`, `'size' must be an integer`, out-of-range paging) | `errors` for range violations |
| 404 | `model-not-found` | No model with that id | |
| 409 | `model-name-taken` | Name already used | |
| 415 | `about:blank` | Content type is not `application/json` | |
| 500 | `internal-error` | Unexpected failure: logged server-side, no internals returned | |

## Reference registration API

| Method | Path | Success | Errors |
|--------|------|---------|--------|
| `POST` | `/api/v1/models/{id}/reference` | `201` + `Location` + reference | `400`, `404`, `413`, `415`, `422`, `502`, `503` |
| `GET` | `/api/v1/models/{id}/reference` | `200` current reference | `404` (`model-not-found`, `reference-not-found`) |

```bash
curl -F file=@reference.csv localhost:8080/api/v1/models/$MODEL_ID/reference
curl -F file=@reference.csv -F 'options={"exclude": ["customer_id"]}' \
     localhost:8080/api/v1/models/$MODEL_ID/reference
```

Request (`multipart/form-data`): `file` (the reference CSV) and optional
`options`, a JSON
[`ProfileOptions`](../analytics/README.md#profileoptions) object passed to the
engine unchanged. The backend checks only that `options` is a JSON object;
the engine validates its content.

```json
{"id": "...", "modelId": "...",
 "dataset": {"id": "...", "sha256": "...", "byteSize": 14231, "originalFilename": "reference.csv"},
 "rowCount": 500, "engineVersion": "0.1.0.dev0",
 "columns": [
   {"name": "age", "logicalType": "numeric", "monitored": true, "excludedReason": null},
   {"name": "customer_id", "logicalType": "categorical", "monitored": false,
    "excludedReason": "likely_identifier"}],
 "issues": [], "createdAt": "2026-11-21T17:02:11.123456Z"}
```

`columns` shows how the engine understood each column, so a wrong inference
(e.g. a numeric id) is visible immediately and can be fixed with
`options.overrides` / `options.exclude`. The full profile, which can be
several MB, is not returned; it is stored for drift runs.

**How it works**

1. Check the model, then stream the file into the content-addressed store
   (no database transaction).
2. Send the stored file to the engine's `/v1/profile` and wait. This is
   synchronous and can take minutes for a 100 MB file; the client's read
   timeout is 5 minutes.
3. Only if the engine succeeds, insert the `dataset` row (role `REFERENCE`)
   and the `reference_profile` row (profile and issues as `JSONB`) in **one
   transaction**. The database therefore holds only successfully profiled
   references; a failed attempt leaves no rows, and the error goes back to the
   client.

Registering again keeps the old reference and makes the new one current, so
earlier drift runs stay reproducible. The database guarantees that a
reference points at a `REFERENCE` dataset of the same model (a composite
foreign key on `(dataset_id, model_id, role)`).

**Errors specific to this endpoint**

| Status | `type` suffix | When |
|--------|---------------|------|
| 400 | `empty-upload`, `invalid-upload`, `invalid-request`, `invalid-parameter` | Empty file, bad file name, missing `file` part, `options` not a JSON object |
| 413 | `upload-too-large` | Over the multipart limit, the file store's limit, or the engine's limit |
| 422 | *the engine's type*: `invalid-csv`, `empty-dataset`, `invalid-options`, `unprofilable-dataset` | The engine rejected the data; `detail` and `errors` are passed through |
| 502 | `analytics-protocol-error` | The engine's response broke the contract (logged) |
| 503 | `analytics-unavailable` | Engine down or timed out; `Retry-After: 30`. The engine's address is logged, never returned |

## Monitoring runs

A monitoring run compares one uploaded **current** batch with the model's
reference profile on a background worker (package `run`).

| Method | Path | Success | Errors |
|--------|------|---------|--------|
| `POST` | `/api/v1/models/{id}/runs` | `202 Accepted` + `Location` + run (`PENDING`) | `400`, `404`, `409`, `413`, `415`, `503` |
| `GET` | `/api/v1/runs/{runId}` | `200` run | `400` (malformed id), `404` (`run-not-found`) |

```bash
curl -i -F current=@today.csv localhost:8080/api/v1/models/$MODEL_ID/runs
curl -F current=@today.csv -F 'config={"numeric": {"psi_threshold": 0.25}}' \
     localhost:8080/api/v1/models/$MODEL_ID/runs
curl localhost:8080/api/v1/runs/$RUN_ID        # poll until SUCCEEDED or FAILED
```

Request (`multipart/form-data`): `current` (the batch CSV) and optional
`config`, a JSON [`DriftConfig`](../analytics/README.md#api) (for example
`{"numeric": {"psi_threshold": 0.25}, "dataset_drift_share": 0.5}`) passed to
the engine unchanged. The backend checks only that `config` is a JSON object;
the engine checks its content **when the run executes**, so an invalid value
gives a `FAILED` run with `invalid-config`, not a `400`.

The `POST` answers immediately, before the comparison runs. Poll the
`Location` until `status` is `SUCCEEDED` or `FAILED`:

```json
{"id": "...", "modelId": "...", "referenceId": "...",
 "currentDataset": {"id": "...", "sha256": "...", "byteSize": 9983, "originalFilename": "today.csv"},
 "status": "SUCCEEDED",
 "requestedConfig": {"numeric": {"psi_threshold": 0.25}},
 "result": {"engineVersion": "0.1.0.dev0", "profileEngineVersion": "0.1.0.dev0",
            "rowCount": 800,
            "summary": {"n_features": 2, "n_evaluated": 2, "n_insufficient_data": 0,
                        "n_drifted": 1, "n_with_quality_flags": 0,
                        "drift_share": 0.5, "dataset_drift": true},
            "config": {"numeric": {"psi_threshold": 0.25, "...": "..."}, "...": "..."},
            "issues": [], "warnings": []},
 "error": null,
 "createdAt": "...", "startedAt": "...", "finishedAt": "..."}
```

`result` is set only for `SUCCEEDED` runs and `error` only for `FAILED`
runs: `{"type": "urn:driftwatch:problem:schema-mismatch", "message": "...",
"details": [...]}`. Branch on `error.type`. Per-feature results are stored
but not returned yet (task 2.8). `result.config` is the complete config the
engine applied, with defaults filled in, so a run can be repeated exactly.

**Errors specific to these endpoints**

| Status | `type` suffix | When |
|--------|---------------|------|
| 400 | `empty-upload`, `invalid-upload`, `invalid-request`, `invalid-parameter` | Empty file, bad file name, missing `current` part, `config` not a JSON object |
| 404 | `model-not-found`, `run-not-found` | Unknown model or run |
| 409 | `reference-required` | The model has no reference dataset yet |
| 413 | `upload-too-large` | Batch over the upload limit |
| 503 | `run-capacity-exceeded` | All workers busy and queue full; nothing was stored; `Retry-After: 30` |

```text
PENDING ──► RUNNING ──► SUCCEEDED   (engine's complete result stored)
   │           └──────► FAILED      (reason stored: error_kind + message)
   └──────────────────► FAILED      (interrupted by a restart)
```

**Submitting** (`RunService.submit`):

1. Reserve a place in the bounded executor. If all workers are busy and the
   queue is full, refuse at once (`503 run-capacity-exceeded`): nothing is
   stored.
2. Look up the model's current reference. The run is **pinned** to it, so
   registering a newer reference while a run waits does not change what the
   run compares against. No reference → `409 reference-required`.
3. Store the file (no transaction open), then insert the `CURRENT` dataset
   and the `PENDING` run in one transaction.
4. After the commit, hand the run to a worker.

**Executing** (`RunWorker`):

1. Claim the run with one conditional `UPDATE … WHERE status = 'PENDING'`,
   so a run is started at most once.
2. Send the stored profile (unchanged) and the stored batch to the engine's
   `/v1/drift`, with no transaction open.
3. In one short transaction, store either the full response (`SUCCEEDED`) or
   the reason (`FAILED`). A response without `engine_version`, `n_rows`,
   `summary` or `features` is treated as a contract violation, not a success.

| Failure | `error_kind` | Stored message |
|---------|--------------|----------------|
| Engine rejected the batch | the engine's problem kind, e.g. `schema-mismatch`, `invalid-csv`, `invalid-config` | the engine's `detail`; its `errors` in `error_details` |
| Engine down or timed out | `analytics-unavailable` | generic (the engine's address is only logged) |
| Response broke the contract | `analytics-protocol-error` | generic (details logged) |
| Anything else | `internal-error` | generic (stack trace logged) |
| Backend restarted mid-run | `interrupted` | "submit the batch again" |

Runs are **not retried automatically**: a rejection would fail again, and
re-sending a large batch doubles the engine's load. The client resubmits.

**Restarts.** The queue is in memory. At startup, before the web server
accepts requests, `RunRecovery` marks every `PENDING` or `RUNNING` run
`FAILED` (`interrupted`), so no run stays unfinished forever. This assumes a
**single backend instance**; several instances sharing a database would need
a lease or owner column first.

**Database guarantees (Flyway V4).** Check constraints make each status
carry exactly its fields (a `SUCCEEDED` run always has a result and engine
version, a `FAILED` run always has a reason and never a result, a `PENDING`
run has not started). Composite foreign keys ensure the compared dataset is
a `CURRENT` dataset of the same model and the reference belongs to the same
model. Each batch belongs to one run.

| Property | Default | Meaning |
|----------|---------|---------|
| `driftwatch.runs.concurrency` (`DRIFTWATCH_RUNS_CONCURRENCY`) | `2` | Runs sent to the engine at once (each holds a whole batch in the engine's memory) |
| `driftwatch.runs.queue-capacity` (`DRIFTWATCH_RUNS_QUEUE_CAPACITY`) | `20` | Accepted runs that may wait for a worker |

## Dataset storage

Uploaded CSV files are kept in a **content-addressed file store**
(`dataset.ContentAddressedFileStore`); each upload is recorded as a row in
`dataset` (Flyway V2). Reference registration and monitoring runs (above) use it.

Uploads are limited twice: Spring's multipart parser
(`spring.servlet.multipart.max-file-size`, set to the same value) rejects
them while parsing, and the file store re-checks while streaming.

| Property | Default | Meaning |
|----------|---------|---------|
| `driftwatch.datasets.storage-root` (`DRIFTWATCH_DATASETS_STORAGE_ROOT`) | `storage/datasets` (relative; local development only) | Root directory of the file store |
| `driftwatch.datasets.max-upload-size` (`DRIFTWATCH_DATASETS_MAX_UPLOAD_SIZE`) | `100MB` | Per-file limit; matches the analytics engine's |

Both are validated at startup.

**How a file is stored**

1. The bytes are streamed into `<root>/.tmp` while their SHA-256 and size
   are computed, so a file is never held in memory. Crossing the size limit
   stops the copy at once (tested with an endless stream).
2. The file is made read-only and moved atomically to
   `<root>/<h[0:2]>/<h[2:4]>/<h>`, so readers never see a partial file.
   Identical content is stored once; two uploads of the same bytes are two
   `dataset` rows pointing at one file.
3. Only then is the `dataset` row inserted, in a short transaction. No
   database connection is held while a large upload streams in.

**Safety**

- Addresses must be lower-case 64-character hex, so a crafted hash cannot
  reach outside the store (`../` is rejected). The client's file name is
  metadata only and is never used to build a path.
- The storage path is derived from the hash, not stored, so the root can
  move without a data migration.
- If the row insert fails after the file was stored, the file remains as an
  unreferenced blob. That is harmless, because a later identical upload
  reuses it; removing such blobs is left to a future clean-up job.
- CSV content is not parsed here. Parsing rules live in one place, the
  analytics engine, which validates the file during profiling (2.6).

## Analytics engine client

`analytics.AnalyticsClient` calls the engine's `GET /health`,
`POST /v1/profile` and `POST /v1/drift`
([contract](../analytics/README.md#api)). It uses Spring's `RestClient` on
the JDK HTTP client; files are sent as multipart resources, and the profile
is sent as a file part, as the engine requires.

| Property | Default | Meaning |
|----------|---------|---------|
| `driftwatch.analytics.base-url` (`DRIFTWATCH_ANALYTICS_BASE_URL`) | `http://localhost:8000` | Engine address |
| `driftwatch.analytics.connect-timeout` | `2s` | Fail fast when the engine is down |
| `driftwatch.analytics.read-timeout` | `5m` | Profiling a 100 MB CSV is CPU-bound and can take minutes |

**Every failure is one of three exceptions**, so callers decide what to do
by type:

| Exception | When | Caller should |
|-----------|------|---------------|
| `AnalyticsRejectedException` | Engine returned a DriftWatch 4xx problem (`invalid-csv`, `schema-mismatch`, `upload-too-large`, …). Carries status, `kind`, detail and `errors`. | Show it to the user; retrying will not help |
| `AnalyticsUnavailableException` | Connection refused, timeout, 5xx | Mark the work as failed or retry later |
| `AnalyticsProtocolException` | Contract violation: 2xx with invalid JSON, 4xx without a DriftWatch problem body (e.g. `about:blank` 404), missing fields | Treat as a bug or an engine version mismatch |

The client **never retries**. The engine is stateless, so a repeat is safe,
but re-sending a 100 MB upload doubles the load; the run lifecycle (2.7)
decides. Responses are returned as JSON trees: the engine owns its data
model, and the backend stores profiles and results as JSON.

**Tests**

- `AnalyticsClientTest` uses a stub HTTP server (the JDK's `HttpServer`)
  for the request format, all three error types, a refused connection, a
  read timeout and a 32 MB upload.
- `AnalyticsEngineContractTest` runs against the **real** engine when
  `DRIFTWATCH_ANALYTICS_URL` is set (otherwise it is reported as skipped):

  ```bash
  (cd ../analytics && .venv/bin/uvicorn driftwatch_analytics.main:app --port 8000) &
  DRIFTWATCH_ANALYTICS_URL=http://127.0.0.1:8000 ./mvnw verify
  ```

  CI runs every `*EngineContractTest` (this one and the end-to-end reference
  registration test) in the `engine-contract` workflow whenever `analytics/`
  or `backend/` changes, so a change on either side that breaks the contract
  fails the build.

## Operational endpoints

| Method | Path | Response |
|--------|------|----------|
| `GET` | `/actuator/health` | `200 {"status":"UP", "groups":["liveness","readiness"]}` |
| `GET` | `/actuator/health/liveness` | `200 {"status":"UP"}` while the process runs |
| `GET` | `/actuator/health/readiness` | `200` when the database is reachable, `503` otherwise |
| `GET` | `/actuator/info` | Build artifact, group, name and version |

**Readiness vs. liveness:** readiness includes the database check, so load
balancers stop routing traffic during a database outage. Liveness does not,
so an orchestrator does not restart a healthy process just because the
database is down (a test stops the database and checks both).

**Exposure policy** (see `application.yml`): only `health` and `info` are
exposed over HTTP. Endpoints such as `env`, `beans`, `configprops`,
`heapdump`, `loggers` and `mappings` can leak configuration or memory
contents, so they stay unexposed; a test checks that each returns 404.
Health hides component details, and info omits the server's Java and OS
details. The build time is left out of build info, because the Spring Boot
parent fixes timestamps for reproducible builds and the value would always
read 1980.
