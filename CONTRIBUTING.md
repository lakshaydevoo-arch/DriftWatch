# Contributing to DriftWatch

## Workflow

1. Pick a task from [DEVELOPMENT_ROADMAP.md](DEVELOPMENT_ROADMAP.md).
   Large tasks are split until each piece can be tested on its own.
2. Implement it with tests and documentation in the same change.
3. Before committing:
   - `git status` and review the full diff,
   - run the tests and linters for every module you touched (below),
   - check for secrets, credentials, large data files or build output,
   - update the module README, `DEVELOPMENT_LOG.md` and, for user-facing
     changes, `CHANGELOG.md` (`Unreleased` section).
4. Commit one logical change per commit.

Never commit failing tests, skipped tests without a written reason, or
unfinished features. Do not amend published commits or force-push.

## Commit messages

[Conventional Commits](https://www.conventionalcommits.org/):

```
<type>(<optional scope>): <imperative summary, ≤ 72 chars>

<optional body: what and why, not how>
```

| Type | Use for |
|------|---------|
| `feat` | New functionality |
| `fix` | Bug fixes |
| `test` | Adding or improving tests only |
| `docs` | Documentation only |
| `refactor` | Code change with no behaviour change |
| `chore` | Build, configuration, dependencies, CI |

Scopes: `analytics`, `backend`, `frontend`, `ci`, `docs`.

Examples:

```
feat(analytics): add PSI-based drift detection
test(analytics): add categorical drift edge-case tests
docs: document monitoring API contracts
```

## Quality checks per module

These commands become available as each module is scaffolded. CI runs the
same commands (`.github/workflows/`), so a change that passes locally should
pass in CI. If you change dependencies, regenerate the module's lock file
(see `analytics/README.md`) in the same commit.

If you change the engine's API or the backend's client, also run the
backend's `AnalyticsEngineContractTest` against a running engine (see
`backend/README.md`); CI runs it in the `engine-contract` workflow.

| Module | Format / lint | Tests |
|--------|---------------|-------|
| `analytics` | `ruff format --check .` · `ruff check .` · `mypy` | `pytest` |
| `backend` | `./mvnw spotless:check` | `./mvnw verify` (unit + Testcontainers integration tests; needs Docker) |
| `frontend` | `npm run lint` · `npm run format:check` · `npm run typecheck` | `npm test` |

## Testing expectations

- Unit tests for all statistical logic, including edge cases
  (empty input, all-missing, constant columns, unseen categories).
- Statistical tests use seeded synthetic data or real public datasets —
  never hardcoded "expected" metrics copied from a previous run without
  an independent justification.
- Integration tests for every public API workflow.
- Tests must be deterministic. Flaky tests are bugs.

## Secrets and data

- No credentials, tokens or `.env` files in Git. Use `.env.example` for
  documenting variables.
- No large or private datasets in Git. Test data is generated by seeded code
  or small fixtures (< 1 MB) with a stated origin.

## Code style

- Java: Google Java Style via Spotless.
- Python: ruff defaults, type hints on public functions.
- TypeScript: strict mode, ESLint + Prettier.
- Settings shared across editors are in [.editorconfig](.editorconfig).
